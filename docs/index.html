from Infernux import InxComponent, Vector3, serialized_field


class Spin(InxComponent):
    speed: float = serialized_field(default=90.0, range=(0.0, 360.0))

    def update(self, delta_time: float) -> None:
        self.transform.rotate(Vector3(0.0, self.speed * delta_time, 0.0))

NEURAL NETWORK-NATIVE ENGINE · 3N

Neural Network-Native Engine (3N) is our destination: models should work with world data and simulation as part of the engine. Python, batch APIs and CPU/GPU compute form the foundation; portable inference, replay and the full tensor data plane are next.

WHY 3N

A playable world. A learning environment. One engine.

A neural-native engine connects the game you build to the data a model needs. Infernux is developing that connection from world representation through simulation and tools to deployment.

CREATE

Start with a world worth playing

Scenes, materials, animation, physics, audio and UI turn an idea into an interactive world. Python lets gameplay and custom tools grow together as your project takes shape.

CONNECT

Bring computation into the simulation

Batch APIs expose world state to Python. CPU/GPU JIT and Taichi integration support computational gameplay. These are foundations for richer model interaction with the world.

ROADMAP

Make neural systems part of the game

The next stages connect model workflows, portable inference, replay and batch environments. The destination is a repeatable route from experimentation to a model-powered game on the target device.

Technology showcase

A voxel continent of 65,536 objects, built in the editor and rendered in the editor.

Not an offline render and not a concept image. Those blocks are ordinary GameObjects going through the ordinary Scene and Hierarchy, with no dedicated batching path. The tilt-shift, fog and colour on top are a RenderStack written in Python.

What is in this frame

  • 65,536 standard GameObjects sharing one mesh and one material. You can still select them in the Hierarchy and edit them. They are no different from a cube you dropped in by hand.
  • Tilt-shift focus, distance fog, height fog, colour controls and MSAA all come from one custom RenderStack. Change it in the editor and you see the result immediately.
  • The raw editor capture. Nothing retouched.
DESIGN PRINCIPLES

Built for authors. Open to inspection.

A clear division of work keeps everyday iteration fast and ambitious systems understandable.

1 · A complete game workflow

Import content, assemble scenes, tune behavior and export a Player. Rendering, resources, physics and tools work together around the game you are making.

2 · Python authors, C++ executes

Use Python for gameplay, editor extensions, render authoring and computation. C++ and the GPU handle the performance-critical runtime work behind those interfaces.

3 · Explicit, observable operations

GUID asset identities, editor commands and transactional reload make changes traceable. The optional MCP plugin lets agents use the editor command and undo paths, with inspectable results.

ENGINE FOUNDATIONS · 0.4.1

SUBSYSTEM · RENDER

Vulkan and WebGPU

Native Players use Vulkan; browser Players use WebGPU. Python defines the RenderStack and C++ runs the render graph. Shared scene and material data feed platform rendering, including lighting, shadows, UI, and particles.

SUBSYSTEM · GPU VFX

Particle Graph on the GPU

GPU Particle Graph: an emitter plus Init, Update and Rendering stages. The typed graph compiles to runtime IR ahead of time, outputs sprites or meshes, and previews in the editor with parameters you can drag while it runs.

SUBSYSTEM · PHYSICS

Jolt physics

Jolt. Rigid bodies, colliders, scene queries, collision callbacks, layer filtering, transforms kept in sync with the scene. Its job system runs on the engine's own thread pool rather than spawning threads of its own.

PREVIEW · ANIMATION

2D and 3D animation

2D clips and sprite playback, embedded or separate FBX takes, skeletal animation, skinned meshes, state-machine graphs, and Timeline. Matching FBX joints map exactly, with importer pivot helpers handled and incompatible rigs rejected.

SUBSYSTEM · EDITOR

An editor you can extend

Work across Scene/Game views, Hierarchy, Inspector, Project, Console, UI, animation and graph tools. Add your own dockable panels and nested menus while using the shared selection, commands and undo workflow.

SUBSYSTEM · SCRIPT

Python gameplay layer

Python components, Inspector fields, coroutines and prefabs support everyday gameplay. Transactional reload refreshes project and plugin components, including behavior on existing instances.

SUBSYSTEM · ASSETS

Assets and project pipeline

Project and package assets share GUID identities and live refresh. Player content stays in Content.inxpkg instead of exposing the authoring directory tree. Engine asset APIs resolve paths through the cooked index, with filesystem access for payloads that need it.

SUBSYSTEM · DATA PLANE

World data meets computation

Read and write world properties in batches through NumPy arrays. CPU/GPU JIT and Taichi integration let project scripts run numerical workloads, with target preparation and reusable warmup results.

SUBSYSTEM · PLUGINS · MCP

InxPackage plugins and MCP

Package components, tools and assets as .inxpkg. Runtime and Editor roles keep shipped code separate from authoring services. Add localized panels and menus, or use the optional MCP plugin to automate editor operations.
