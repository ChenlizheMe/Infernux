WHAT IS 3N

3N is a game engine where neural networks are native.

Most engines treat AI as a plugin, bolted on after the game is finished. A 3N engine is built for models from the first line: the world is data they can read, the simulation is a place where they can act, and the shipped game is somewhere they can run.

NEURAL NETWORK NATIVE 3N
  1. 01 NEURAL

    Models are part of the cast

    A neural network lives in the scene like any component. It observes state, chooses actions, and is debugged in the same editor as your gameplay code.

  2. 02 NETWORK

    The world speaks in tensors

    World data moves between simulation and models in batches, without per-object glue code. Many environments step side by side for training and evaluation.

  3. 03 NATIVE

    Built in, not bolted on

    Inference, replay and deterministic stepping belong to the runtime itself, and ship with the Player on every target platform.

ROUTE TO 3N

A playable world. A learning environment. One engine.

Each stage keeps the game playable while the model side grows. Infernux is building the link from world representation through simulation and tools to deployment.

STAGE 01 · CREATE

Start with a world worth playing

Scenes, materials, animation, physics, audio and UI turn an idea into a world people want to play. Python lets gameplay and custom tools grow together as the project takes shape.

STAGE 02 · CONNECT

Bring computation into the simulation

Batch APIs expose world state to Python, and CPU/GPU JIT with Taichi powers computational gameplay. This is the data path models will use.

STAGE 03 · NATIVE

Make neural systems part of the game

Next: model workflows, portable inference, deterministic replay and batched environments, ending in a model-powered game that ships on the target device.

DESIGN PRINCIPLES

Built for authors. Open to inspection.

A clear division of work keeps everyday iteration fast and ambitious systems understandable.

1 · A complete game workflow

Import content, assemble scenes, tune behavior and export a Player. Rendering, resources, physics and tools work together around the game you are making.

2 · Python authors, C++ executes

Use Python for gameplay, editor extensions, render authoring and computation. C++ and the GPU handle the performance-critical runtime work behind those interfaces.

3 · Every operation is visible

GUID asset identities, editor commands and transactional reload make changes traceable. The optional MCP plugin lets agents use the editor command and undo paths, with inspectable results.

ENGINE FOUNDATIONS · 0.4.1

From an idea to an interactive world.

Python gameplay, native rendering and physics, imported content and tools you can extend. The 041 line deepens multi-scene editing, compute, world-space UI and live plugin authoring.

SUBSYSTEM · RENDER

Vulkan and WebGPU

Native Players use Vulkan; browser Players use WebGPU. Python defines the RenderStack and C++ runs the render graph. Shared scene and material data feed platform rendering, including lighting, shadows, UI, and particles.

SUBSYSTEM · GPU VFX

Particle Graph on the GPU

GPU Particle Graph: an emitter plus Init, Update and Rendering stages. The typed graph compiles to runtime IR ahead of time, outputs sprites or meshes, and previews live in the editor while you drag its parameters.

SUBSYSTEM · PHYSICS

Jolt physics

Jolt: rigid bodies, colliders, scene queries, collision callbacks and layer filtering, with transforms kept in sync with the scene. Its jobs run on the engine's own thread pool instead of spawning threads of their own.

PREVIEW · ANIMATION

2D and 3D animation

2D clips and sprite playback, embedded or separate FBX takes, skeletal animation, skinned meshes, state-machine graphs, and Timeline. Matching FBX joints map exactly, with importer pivot helpers handled and incompatible rigs rejected.

SUBSYSTEM · EDITOR

An editor you can extend

Work across Scene/Game views, Hierarchy, Inspector, Project, Console, UI, animation and graph tools. Add your own dockable panels and nested menus while using the shared selection, commands and undo workflow.

SUBSYSTEM · SCRIPT

Python gameplay layer

Python components, Inspector fields, coroutines and prefabs support everyday gameplay. Transactional reload refreshes project and plugin components, including behavior on existing instances.

SUBSYSTEM · ASSETS

Assets and project pipeline

Project and package assets share GUID identities and live refresh. Player content stays in Content.inxpkg instead of exposing the authoring directory tree. Engine asset APIs resolve paths through the cooked index, with filesystem access for payloads that need it.

SUBSYSTEM · DATA PLANE · 3N

World data meets computation

Read and write world properties in batches through NumPy arrays. CPU/GPU JIT and Taichi integration let project scripts run numerical workloads, with target preparation and reusable warmup results.

SUBSYSTEM · PLUGINS · MCP

InxPackage plugins and MCP

Package components, tools and assets as .inxpkg. Runtime and Editor roles keep shipped code separate from authoring services. Add localized panels and menus, or use the optional MCP plugin to automate editor operations.
