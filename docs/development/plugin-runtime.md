# 插件、资源和脚本的当前执行流程

这份说明对应当前源码。引擎不维护历史脚本实现或历史资源格式的迁移链。
项目应固定引擎和插件版本，主动升级时调整项目源码和资源。

## 游戏开发者的工作流

在插件管理器选择插件并安装。官方目录和 GitHub Release 解析器按照当前引擎版本的
`engine` 要求选择兼容版本。安装后，项目记录实际安装的版本；目录刷新不会偷偷修改
已经安装的文件。主动更新时，再选择兼容的新版本。

直接修改项目中的脚本和资源即可，不需要生成另一份“开发源码”。保存后，引擎合并
文件通知，在安全的执行边界处理变更。编译工作放到后台；模块执行、场景绑定、组件
初始化和编辑器贡献发布在引擎线程进行。

更新插件时，发布者文件、对应的 meta 和发布者配置以新包为准，新包删除的旧成员也会
删除。用户自己增加的文件保留。不做文本合并、本地修改冲突确认或旧包下载。需要长期
保留的定制代码应放在自己的文件或插件中。真正的 GUID 或路径归属冲突仍会报告错误。

文件写入失败时，安装操作撤销自己尚未完成的文件改动；这不代表运行中的旧脚本会被
重新启用。新插件启动失败时，修复当前源码后重新加载。

插件中的某个资产导入或加载失败时，插件管理器显示具体文件及错误，公共插件状态也
提供 `asset_errors`。这不卸载无关且正常工作的代码或资源；`loaded` 只表示代码装配，
不能单独代表整个插件可用。修复资产后，状态随资源系统的实际结果更新。

## 插件作者的工作流

沿用普通 `inx_package.json`、`editor/`、`runtime/`、`plugin_pages/` 和
`requirements.txt`。在 manifest 中声明包标识、版本和引擎要求。运行时代码和资产必须
能够在目标 Player 平台执行；编辑器工具与界面放在 `editor/`。

使用 `InxPreload` 安装服务，用传入的 `PreloadContext` 注册更新、清理和 Python 库。
公开操作注册到引擎的 `OperationRegistry`，不要依赖 MCP 的私有实现。MCP 启停不改变
公共操作属于哪个插件。

```python
from infernux.lifecycle import InxPreload
from infernux.host import OperationRegistry
from infernux.host.operation_support import operation
from infernux.host.operations import OperationKind


class SceneTools(InxPreload):
    def preload(self, context):
        # 注册发生在当前源码的生命周期内，退休时会自动注销。
        OperationRegistry.instance().register(operation(
            "studio.counter.read", OperationKind.QUERY,
            "读取本插件的计数", lambda: {"value": 0},
            capability="studio.read", owner="studio/tools",
        ))
        # 对自己创建的线程、进程和外部资源，显式登记停止方法。
        # context.add_cleanup(service.close)
```

声明的组件字段在重新构造时恢复，新增字段使用新默认值；组件和资源的稳定身份保留。
任意 Python 私有成员、生成器栈和外部库内部状态不会被自动搬到新对象里。需要保留的
状态应当使用明确的数据字段或由插件自己管理。

引擎可清理自己管理的组件、协程、Signal、更新注册、服务、操作、队列回调和编辑器贡献。
插件自行启动的线程、第三方原生库及外部进程，应通过 `add_cleanup` 正常关闭。原生库
不能安全卸载时，需要重启编辑器；不把这种情况伪装成热重载成功。

普通 Python 导入的二进制扩展作为明确的原生依赖登记。首次加载不要求重启；二进制
未变时，Python 脚本仍可正常重载。更新或卸载要改动已加载的扩展文件时，停止相关
入口，沿用现有挂起安装流程，在下一次干净启动前完成文件发布。外部改动扩展文件也
会先停止相关入口，即使后续资源导入失败。不会强行卸载映射中的库或继续调用其旧实现。
自行通过第三方接口加载、引擎无法观察的原生库，由作者使用 `context.require_restart`
说明重启要求，并登记必要的清理。

## 热重载的单一路径

`ResourcesManager` 将资源保存和内部资源修改送入同一个 `ReloadCoordinator`。
协调器负责依赖图、包初始化器、循环依赖、精确源码快照和当前发布状态。

1. 在引擎安全边界退休受影响的模块和注册，组件暂时成为不可执行的缺失脚本占位。
2. 后台编译当前源码，较早的编译结果不能覆盖较新的保存。
3. 按依赖顺序构造当前模块，先发布所有当前类型并完成同批组件绑定，再初始化插件领域对象。
4. 完成全部反序列化回调和 Awake 后才执行 Start，最后开放成功对象的准入并启用。
5. 语法、导入或初始化失败时，保持当前内容停用并在 Console 报告；修复后从当前源码
   重新构造。不会通过函数体替换、闭包转发或旧模块继续执行来隐藏失败。

进入 Play 前还会读取已保存的必要脚本及依赖，覆盖文件通知尚未到达的情况。
无关的坏脚本不会阻止正常场景工作。构建时的源码分析使用独立的私有导入表，不发布到
编辑器的模块表，也不借用旧脚本实现。

普通服务、延迟任务和组件都拥有明确的执行寿命。通过公开组件查询或服务查询取得的
脚本对象会建立实际依赖。当前初始化失败会停止有关入口；已提交的 CPU/GPU 工作可以
完成资源退休，但其旧结果不能再应用到世界。Stop 可以在源码有错误时恢复作者文档，
随后修复当前源码仍可重新进入 Play。

## 资源导入与错误

资源仍通过统一的原生 AssetDatabase 导入。文件通知只提交工作；资源发布、文档状态
和场景更新由引擎线程处理。永久性错误不会被改写成“稍后就绪”并反复重试。
真正的原子写入、目录更新和正在提交的本地写入可以等待其完成。

源文件存在而 meta 缺失或损坏时，重新导入并重新生成元数据。优先保留资源目录已知的
GUID，其次使用完整可解析元数据中的合法 GUID；二者都不存在才生成新 GUID。不会猜测
破损文本中的身份，也不为新版包已经删除的资源重新生成文件。

脚本、资源、插件或场景的普通加载错误留在可用的编辑器中报告，成功导入后清除对应
错误。编辑器先建立核心界面，再加载项目内容。损坏场景不会让整个启动过程退出。
这不意味着损坏的源资产可以无损恢复，也不意味着可以捕获任意原生进程崩溃。

当前失败会使新加载、预览和消费入口不可用，不把旧缓存冒充当前成功结果。已经提交
的 GPU 帧和音频 voice 持有各自合法资源直到完成。修复源文件或依赖后走同一发布流程；
可重建的 Library 产物从当前源重建。没有未保存修改的外部场景更新自动加载，有草稿时
保留草稿并让用户选择。

## 主题

打开“编辑 → 主题”选择内置主题或普通插件贡献的主题。选择保存在编辑器偏好中。
颜色、间距和布局数值来自同一个原生注册表，Python 界面同步读取。
主题不修改游戏 UI 默认值、材质或 Player 画面。

安装、更新、启停和卸载主题统一在插件管理器完成，使用独立的“主题”分类。
主题窗口负责搜索、筛选和选择已发现的主题，以列表和详情展示作者、说明、来源插件、
版本、文件位置和可用状态。选择后直接在实际编辑器应用，不另设预览区域。“管理插件”直接打开主题分类；具体主题
也可以跳到所属插件。主题窗口不另设安装流程。

主题还可覆盖 `PANEL_*`、`BUTTON_*` 的渐变、分层边框、切角和微光，以及
`SURFACE_GRAIN_*` 纸面底纹、`SURFACE_HEX_*` 六边形底纹。它们使用同一份 token 表，
默认关闭。底纹通过原生纹理上传管线首次生成并缓存，内容和文字画在其上；颜色切换不重建字体。
具体参数见主题模板 README，导出的 `theme-tokens.json` 自动包含当前支持的全部选项。

主题作者从专用模板开始：

```powershell
python scripts/plugins/export_theme_template.py out/templates/my-theme
python out/templates/my-theme/package.py build out/my-theme.inxpkg
```

模板只安装 `package/` 内的主题数据；外层 README、打包工具、token 列表和 GitHub
workflow 不进入项目。模板附有普通 Release 发布流程。损坏主题停止贡献，编辑器使用
内置样式；修复后重新应用保存的选择。

## MCP、公共 Host 与外部 harness

引擎 Host 拥有场景、输入、资源、截图、构建和 Player 控制。轻量的
`infernux_automation` 客户端只使用 Python 标准库，既可随引擎使用，也可单独安装到
harness 环境。独立 MCP 服务通过它连接引擎，不导入原生引擎库。

引擎启动公共本机接口，启用 MCP 插件后另起标准 MCP 进程。端口自动分配，描述文件位于
项目的 `Cache/Automation/`，不争用固定默认端口。标准 stdio 也可用。所有连接绑定
明确的项目和引擎实例，重启后显式重连。未知结果的写操作不自动重发。

MCP 提供工具发现、schema、调用、顺序批处理、后台任务、资源和常用流程。
`load_and_capture` 等待场景加载和真实 GPU 截图完成，不靠固定延时猜测就绪状态。
插件的独立说明记录了 Claude Code、Codex、DSH 和 WorkBuddy 的配置生成方式。

排队的任务绑定提交时的操作实现。该实现被卸载或替换后，旧请求明确失败，不会悄悄
改为执行同名的新实现。已开始执行的世界修改仍按实际结果处理。

独立 MCP 进程通过文件事件观察自身及轻量 SDK 的 Python 源码。源文件保存、删除或
移动后停止当前服务，关闭观察并提示重新启动；不会继续执行内存中的旧代码，也不会
自动重放操作。这个停止只影响 MCP 连接，不关闭附着的编辑器或撤销已应用的修改。

查询按信号更新，可指定信号，也可使用对应领域的默认信号。跨轮汇报区分结果变化与
真实用户轮次：harness 提供稳定会话 ID 和每轮 ID，相同轮次不会重复扣次数。
Claude 的公开输入 hook 可自动接入；其它客户端在没有输入 hook 时，通过标准工具和
显式轮次入口使用。MCP 通知本身不能强制客户端开始一轮模型推理。

查询由 `stop_observing` 释放。任务取消返回实际结果；已经执行的世界修改不会被声明为
已经撤销。MCP 不维护权限模式、项目副本、旧实现回退或额外的验证记录平台。

普通工具与标准后台 Task 使用同一真实协议会话。会话结束释放它的观察并停止配方尚未
执行的后续步骤，另一会话继续工作。Claude、Codex 和 DSH 的配置合并保留其他服务器
的设置值；TOML 和 YAML 会规范化格式，原注释不保留。WorkBuddy 使用独立 Infernux
Connector 的 `mcp.json`；按照其[公开格式](https://open.workbuddy.cn/en/docs/connector)，
一个 Connector 只配置一个服务。目标文件已有其他服务时不改写，改用独立 Connector
文件。四个客户端的配置格式与协议路径已经检查，未将配置测试称作四个客户端应用的
实机联调。
